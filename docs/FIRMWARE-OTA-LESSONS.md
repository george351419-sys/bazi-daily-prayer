# 固件 OTA 事故复盘：HTTPS 地址被设备端拒绝

日期：2026-10-31

设备：`FRAMEFILMARK-Elink`

升级起点：`3.2.5-ritual.3`，编译指纹 `f6aff2f3...57b92`

目标版本：`3.2.5-ritual.5`，编译指纹 `59972da4...aa2b69b`

## 现象

网页通过蓝牙发起 Wi-Fi 固件升级后立即显示：

```text
尚未确认升级成功：画屏拒绝启动 Wi-Fi 固件下载，错误码 2。
```

设备没有进入 Wi-Fi 连接或下载阶段。重复操作结果一致，因此不是信号弱、密码错误、固件下载超时或目标镜像损坏。

## 根因

蓝牙 `0x57` 命令用于启动 Wi-Fi 直连下载。设备端在创建下载任务前校验 URL：

```c
(strncmp(url, "http://", 7) != 0 && !wifi_cloud_https(url))
```

修复前的 `ritual.3` 只接受字面量 `http://`，而升级页提交的是：

```text
https://playmath.cn/firmware/frame_film_ark-3.2.5-ritual.5.bin
```

固件在解析阶段直接返回 `2`。这里的 `2` 表示请求参数或 URL 无效，不是 Wi-Fi 连接失败。设备已经配置了 `playmath.cn` 的 HTTPS 根证书，但 URL 白名单在证书校验之前就拒绝了请求。

早上升级到 `ritual.3` 时链路曾成功，说明蓝牙、设备 Wi-Fi、下载服务和镜像本身都正常。后来升级入口改为绝对 HTTPS 地址，旧固件中的严格 HTTP 白名单没有同步调整，才出现同一条链路在第一步即失败。

## 修复

网页层在 HTTPS 启动请求被设备以错误码 `2` 拒绝时，只对同一份已签名固件清单改用 HTTP 重试一次：

- `public/ark-network.js`：允许 `http://` 与 `https://playmath.cn/`，仅当首次 HTTPS 返回 `2` 时降级重试。
- `tests/ark-network.test.mjs`：覆盖 HTTPS 被拒后改为 HTTP 的完整 OTA 流程。
- 固件端：URL 校验允许 `https://playmath.cn/`，同时保留证书配置。

无论走 HTTP 还是 HTTPS，下载完成后仍必须校验清单中的文件大小、SHA-256 和重启后的编译指纹。HTTP 回退不是跳过完整性校验。

## 必须记住的规则

1. **OTA 是跨端协议。** 网页、蓝牙命令、设备 URL 白名单和下载客户端必须作为一组变更验收，不能只改一端。
2. **不能只在浏览器单测里验证升级。** 上线前必须用“上一版真实固件”完整走一遍蓝牙发起、Wi-Fi 下载、SHA 校验、重启和指纹核验。
3. **错误码 `2` 先查协议参数。** `0x57` 返回 `2` 表示 Wi-Fi 尚未启动；不要先让用户反复重配 Wi-Fi 或恢复出厂。
4. **协议改动要保留兼容路径。** 新页面应能升级旧设备，旧页面不能依赖新固件才有的行为。
5. **降级必须有边界。** 只允许显式的、单次的 HTTP 回退，并且始终保留目标 SHA-256 与运行指纹校验。
6. **上线前记录版本矩阵。** 至少写清“发起升级的网页版本、运行中的固件版本、目标固件版本、使用的 URL 协议”。

## 回归检查

```sh
node --test tests/ark-network.test.mjs tests/firmware-upgrade-page.test.mjs
```

真实设备验收必须同时确认：

- 页面显示升级成功；
- 重启后运行版本为目标版本；
- 编译指纹与 `elfSha256` 完全一致；
- 断电重启后仍运行目标版本。


## 2026-11-01 同类故障再次出现：必须执行的约束

此前已有这份复盘，但后续生产发布未携带该文档、旧设备兼容路径和相应验收约束，再次向 ritual.5 的 0x57 提交 HTTPS，返回错误码 2。文档存在不能替代发布前读取和自动检查。

本节是当前处理方式，取代上文历史“HTTP 回退”方案；上文仅保留为事故历史。现有发布清单提供 SHA-256，未证实另有数字签名，因此不得称其为“已签名清单”。

- 已核对的 ritual.3 / ritual.5 通过浏览器 HTTPS 下载、文件 SHA-256 校验和 BLE OTA 升级。不得再次直接调用旧固件的 HTTPS Wi-Fi OTA 入口，不得静默改用 HTTP。
- 升级前读取 0x56 的项目、实际 OTA 容量、版本和 ELF 指纹，并检查目标应用镜像的项目、ESP32-S3 芯片标识、长度和摘要。
- BLE 按既有协议分块，初始化后、每 8 包和末尾等待设备处理屏障；失败不得发送提交命令。传输完成不代表升级成功，必须重启并核验目标版本与 ELF 指纹。
- 不得用新版固件的源码推定用户正在运行的旧固件能力。必须核对实际旧版产物或同等可靠的证据。
- 已上线的网页不等于实体设备已经验收。实际刷写、重启、断电重启尚未验证时，必须明确说明，不能称整条升级链路已成功。

回归测试中必须让旧固件的 Wi-Fi OTA 模拟器返回错误码 2，并验证两个已知旧版均走 BLE 路径。任何改变升级路由的提交都运行上述回归命令。
